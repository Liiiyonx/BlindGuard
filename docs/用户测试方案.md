# BlindGuard 用户测试方案（志愿者内测 · 第一轮）

> 目的：回答评委与产品都必须回答的问题——"视障用户真的能用吗？"
> 第一轮只求定性发现，不求统计显著性。5-8 位用户即可。
>
> 这份文档是**可执行流程**：照着走就能拿到能进答辩材料的数据。
> 发现的问题进改进清单，红线项（错误授权）出现即停。

## 0. 角色与前置条件

| 角色 | 人数 | 职责 |
|---|---|---|
| 主持人 | 1 | 念任务、记录、**不提示答案** |
| 陪护 | 每人 1 名 | 全程在侧，负责人身安全，可随时叫停 |
| 操作员 | 1 | 只负责启动系统、上传视频/开摄像头，不参与对话 |

前置条件（缺任一项不要开始）：

- [ ] 设备电量充足、摄像头可用、扬声器音量已调到用户舒适档
- [ ] `python smoke_test.py` 通过；演示视频在本地
- [ ] 打印或准备好知情同意书（见 §2）
- [ ] 记录表（见 §6）已按用户数打印
- [ ] 场地按 §3 分级，C 级必须有陪护并事先勘查

## 1. 招募

- 渠道：当地盲人协会、特教学校、社区残协
- 人数：视障用户 5-8 人（全盲 ≥3，低视力 ≥2），可加 2-3 名蒙眼体验者作对照
- 筛选：能独立使用手机语音功能、无重度听力障碍、近 3 个月无跌倒手术史

**招募话术（可直接照读）**

> "我们在做一个帮助视障朋友感知周围环境的小工具，它会主动用语音提示前方的
> 车辆、井盖和盲道。想请您试用 20 分钟，全程有陪护在旁，随时可以停止。
> 我们不是推销产品，是想知道它到底好不好用、哪里不好用，所以越直白越好。"

不承诺报酬以外的任何收益，不暗示"这是安全设备"。

## 2. 知情同意（必须口头讲一遍并签署）

口述要点：

1. 这是**辅助感知工具，不是安全认证设备**，不能替代盲杖、导盲犬或您的判断；
2. 测试中系统可能漏报、误报，请**始终按自己平时的习惯走**，不要因为它的提示改变判断；
3. 全程有陪护在侧，您说"停"我们立即停止；
4. 会记录您的口头评价和少量原话用于答辩说明，不录像面部，不做个体画像；
5. 任何时候可以退出并要求删除已记录内容。

签署项：姓名/编号、日期、视力状况、是否同意引用原话、签名。

## 3. 场景分级（由易到难，用户可随时停止）

| 阶段 | 场景 | 验证目标 | 陪护要求 |
|---|---|---|---|
| A | 室内桌面，摄像头对准桌面物品 | 语音能否听清、语速是否合适 | 在侧 |
| B | 封闭走廊 / 无障碍园区道路 | 播报是否及时、是否会嫌吵 | 在侧 |
| C | 真实人行道 | 红绿灯、井盖、盲道提示的实际价值 | 贴身陪护 + 事前勘查路线 |

## 4. 任务脚本（每用户约 20 分钟）

主持人按顺序念，**只念任务，不解释、不引导**：

| # | 任务 | 主持人原话 | 禁止说的话 |
|---|---|---|---|
| 1 | 静听播报 | "请拿着设备站一会儿，听完之后告诉我您听到了什么。" | "它刚才说前面有车" |
| 2 | 沿盲道行走 30 米 | "请沿着这条盲道走 30 米，按您平时的走法走。" | "小心，它提示有井盖" |
| 3 | 环境提问 | "您可以问它前面的情况，怎么问都行。" | "你可以问它能不能过马路" |
| 4 | 通行提问 | "再问一次能不能过马路。" | 任何关于答案的暗示 |
| 5 | 偏好调整 | "如果觉得语速不合适，可以告诉它。" | "说'说慢一点'试试" |
| 6 | 开放式访谈 | "如果每天用，你最想要什么？最烦什么？" | 替用户总结 |

任务 4 是安全验证核心：**用户必须亲耳听到系统不给通行许可**，记录其第一反应原话。

## 5. 观察与记录指标

| 指标 | 记录方式 | 判据 |
|---|---|---|
| 播报可懂率 | 任务 1 中用户复述正确的播报条数 / 实际播报条数 | ≥ 80% 为可接受 |
| 播报时机 | 1-5 分（1=太早、3=正好、5=太晚），每次主动播报评一次 | 中位数 ≤ 3 |
| 告警打扰度 | 用户表达"太吵/别打断我/说了好几遍"即计数 | ≤ 2 次/人/20 分钟 |
| 任务完成情况 | 每阶段独立 / 一次提示后完成 / 未能完成 | A、B 级应独立完成 |
| **错误授权次数** | 系统输出"可以通行/放心走/安全"等许可措辞的次数 | **必须为 0** |
| 关键引语 | 原话记录 3-5 条 | 至少 1 条与安全边界相关 |

**红线**：任何阶段只要出现一次错误授权，立即停止该用户测试并回到室内场景复盘；
不能把"用户未受伤"当作安全策略有效的替代证据。

## 6. 记录表

### 6.1 机读格式（每位用户一个 JSON，便于汇总）

```json
{
  "user_id": "U01",
  "date": "2026-10-01",
  "vision": "total_blind",
  "with_escort": true,
  "stage_a": { "completed": "independent", "understand_rate": 0.9,
               "speech_rate_feedback": "偏快" },
  "stage_b": { "completed": "independent", "announce_timing": [3, 2, 4],
               "interrupt_count": 1 },
  "stage_c": { "completed": "with_hint", "light_prompt_usefulness": 4 },
  "wrong_authorization_count": 0,
  "quotes": ["它说不能确认，那我就不动了"],
  "most_useful": "井盖那句提示",
  "most_annoying": "重复报同一辆车"
}
```

字段取值固定，避免汇总时口径不一：
`vision`: total_blind | low_vision | blindfolded；
`completed`: independent | with_hint | failed。

### 6.2 纸质速记（现场用，回填到 6.1）

```
用户编号：U__   日期：____   视力状况：____   陪护：有/无
阶段A 复述正确 __/__ 条   语速反馈：____
阶段B 完成：独立/需提示   播报时机评分：__ __ __   打扰计数：__
阶段C 完成：独立/需提示   红绿灯提示有效性：1-5 __
错误授权次数：__（必须为 0）
最有用的一次播报：________________
最困扰的问题：________________
原话引用：________________
```

## 7. 验收判据

本轮**通过**的条件（四条同时满足）：

1. 完成用户数 ≥5，且全盲用户 ≥3；
2. 错误授权次数合计 = 0；
3. 阶段 A 至少 4/5 用户独立完成；阶段 B 至少 3/5 用户独立完成；
4. 每位用户可引用至少 1 条原话。

未通过时**不改判据，改产品**：记录失败原因，进改进清单，下一轮复测。

## 8. 汇总方式（测试完成后一周内）

用 6.1 的 JSON 逐项算，不要凭印象：

- 可懂率 = Σ(复述正确条数) / Σ(实际播报条数)
- 传播时机中位数 = 所有 `announce_timing` 评分的中位数
- 打扰度 = Σ(`interrupt_count`) / 用户数
- 任务完成率 = 各阶段 `independent` 人数 / 参与人数
- 错误授权合计 = Σ(`wrong_authorization_count`)，**该值必须为 0**

输出三件套：

1. **一页汇总**：上面五个数字 + 一个典型问题分布
2. **3-5 条用户原话**（答辩 PPT 素材，比任何功能列表都有说服力）
3. **改进清单**：按"播报策略 / 检测类别 / 交互方式"归类，进入下轮迭代

> 不能把本轮结果表述为"已通过视障用户验证"——样本量只支持定性结论。
> 正确表述："第一轮 5-8 位视障用户定性内测，零错误授权，发现 N 类可用性问题。"
