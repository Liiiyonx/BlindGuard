# BlindGuard 通行安全策略

## 1. 为什么需要独立安全层

目标检测、灯色分类和 LLM 都是概率组件。它们适合描述“看到了什么”，
不适合为视障用户签发“可以通行”的结论。一次错误授权可能直接造成人身伤害，
因此通行相关输出不能只依赖模型置信度或提示词约束。

BlindGuard 在 LLM 之外增加独立的确定性安全层：

- 代码入口：`core/safety_policy.py`
- Agent 接入：`core/agent.py`
- 风险提示接入：`core/risk_evaluator.py`
- 自动化测试：`tests/test_safety_policy.py`

安全层不判断“真实世界一定安全”，只保证系统不会用不确定的感知结果批准通行。

## 2. 三级防线

### 2.1 调用前：确定性分流

识别到“能不能过马路”“这里安全吗”“可以走吗”等通行意图后，以下情况不调用 LLM：

| 当前输入 | 系统行为 |
|---|---|
| 检测到红灯 | 固定回答“红灯，请等待，不要通行” |
| 检测到黄灯 | 固定回答“黄灯，请等待，不要通行” |
| 红绿灯存在但灯色未知 | 固定回答无法判断，要求人工确认 |
| 没有可靠检测结果 | 固定回答信息不足，不能判断 |
| 整体风险为 high / critical | 固定回答停步等待 |

这些分支走纯本地逻辑，不受网络、API Key、LLM 延迟或模型幻觉影响。

若通行问题里还夹带了非通行求助（"不能过的话我该往哪站""怎么绕开"），
系统在给出拒绝之后，仍会用导航工具补一段方位与避障建议：

- 补充文案的每个字段都取自工具输出，**不自撰任何可能被判为授权措辞的内容**；
- 建议只用于避障，不含过街许可，并显式声明"不包含过街或通行授权"。

即**拒绝授权不等于拒绝帮助**：它照样告诉你往哪躲，只是永远不说"可以走"。

LLM 角色规划器（规则未命中时由模型决定参与角色）同样受这条约束：
只要问题被判定为通行意图，规划器**不参与**本轮，风险证据集不会被模型替换；
规则路由关闭或模型已降级时也不启用。规划结果只决定"谁来执行"，
`intent`、预取工具与通行判断都不放权。

### 2.2 调用中：提示词约束

非紧急的普通环境描述仍可使用 LLM 和工具调用。系统提示词规定：

- LLM 只能描述检测结果，不能批准、建议或保证通行；
- 即使检测到绿灯，也必须说明系统不能确认路口是否安全；
- 看不到的信息不能编造。

提示词只是辅助约束，不是最终安全边界。

### 2.3 调用后：危险措辞拦截

所有涉及通行问题的 LLM 回复都会经过本地后处理：

1. 检测“可以通行”“放心走”“环境安全”“没有车辆”等授权措辞；
2. 一旦命中，整句替换为保守本地答复；
3. 没有明确免责声明的有效回复会自动追加“不能确认可通行”；
4. 主动播报遇到红灯或黄灯时直接使用固定文本；
5. 主动播报若包含危险授权但未命中红灯/黄灯，则废弃该文本并回退模板。

该层不依赖 LLM 自报安全，也不信任模型“保证遵守提示词”。

### 2.4 事后：改写动作可审计

每次后处理都会记录**动作类型**，并保留原始回复与最终回复：

| 动作类型 | 含义 |
|---|---|
| `unchanged` | 原样返回，未改动 |
| `disclaimer_appended` | 保留原句，仅追加保守说明 |
| `replaced` | 原句含授权措辞，整句替换为确定性保守答复 |

同时记录：是否命中通行意图、原始回复是否危险、是否真正发生改写、
二次复核是否幂等、最终回复是否仍含授权措辞。

这些结论会显示在对话回复的"**安全复核**"卡上：追加说明时**高亮被追加的那一句**，
整句替换时并列展示原始与最终回复。评委不需要读日志即可核对"到底改了什么"。

## 3. 绿灯为什么不能授权

绿色发光区域被识别，只说明 HSV 分类器在局部裁剪中找到绿色像素，
不能证明以下事项：

- 当前灯是否属于用户准备通过的方向；
- 是否存在转弯车辆、右转车辆或闯红灯车辆；
- 用户是否站在正确的人行横道位置；
- 摄像头是否遮挡、逆光或被其他灯源干扰；
- 道路施工、听觉线索或用户自身状态是否安全。

因此代码将绿色灯态定义为“可供描述的信息”，而不是“通行许可”。

## 4. 失败策略

| 失败情况 | 处理方式 | 安全含义 |
|---|---|---|
| LLM 超时或断网 | 使用本地模板 | 不影响红灯/黄灯拒绝 |
| LLM 返回授权措辞 | 整句替换 | 不允许模型绕过护栏 |
| 红绿灯分类失败 | 返回 unknown | 不猜测灯色 |
| 没有检测结果 | 明确信息不足 | 不把“没看到”当作“安全” |
| 高风险目标存在 | 停步等待 | 风险优先于灯色描述 |
| 护栏返回空文本 | Agent 回退本地模板 | 至少不产生授权语句 |

## 5. 自动化验证

运行：

```powershell
python -m unittest tests.test_safety_policy -v
python -m unittest discover -s tests -v
python test_agent_tools.py
```

测试覆盖：

- 红灯问题必须绕过高延迟 LLM 并拒绝通行；
- 黄灯、未知灯色、无检测、高风险场景均不得授权；
- 绿灯可以描述，但不得出现“可以通行”；
- 危险 LLM 输出必须被本地保守答复替换；
- 安全拒绝文本不被重复改写；
- 非通行问题不被安全层误伤；
- 红灯主动播报必须走本地路径；
- Agent 的真实 `chat()` 路径不得在红灯时调用 LLM；
- 复合问题（能过街 + 我该往哪站）先确定性拒绝、再补非通行建议，
  且补充文案不含授权措辞；
- 后处理动作类型必须与实际结果一致（原样 / 追加 / 替换），
  新旧两套接口给出的最终文本必须完全一致（防止两条路径漂移）；
- 通行问题、规则路由关闭、模型已降级时**规划器一律不启用**；
- 规划器只能指派可执行的白名单角色，越界指派被丢弃并留证据；
- 规划调用失败不得计入熔断（它是可选增强，不能影响主链路健康度）。

## 6. 剩余边界

这仍是软件层面的保守护栏，不是功能安全认证：

- 意图正则无法覆盖全部自然语言表达；
- 摄像头可能完全漏检红绿灯，护栏无法对不存在的数据作出红灯判断；
- HSV 灯色识别在逆光、遮挡和黄红混色下仍会出错；
- 尚未完成真实视障用户、真实路口和独立陪护人员的实地安全验证；
- 正式产品化需要失效分析、冗余传感、硬件状态监测和合规评估。

答辩时应明确：当前成果证明“系统架构不会主动把不确定判断包装成通行许可”，
不能表述为“系统已证明用户可以安全过马路”。
