当前 Agent 为“本地意图路由 + LLM 角色规划 + 有界工具编排 + 确定性安全守门员”：

- 能力目录声明 10 个角色的职责、权限边界和首选工具；每轮对话经本地意图路由后，
  仅由主责与协作角色（最多 3 个）各执行一个只读工具并写入 `role_contributions`，
  沟通生成器与安全守门员不参与团队执行，而是在收尾阶段以固定台账形式给出沟通说明
  与确定性复核结论；
- **LLM 角色规划**：规则未命中（`intent=general`）时由模型做任务分解，只决定
  参与角色与顺序理由，**工具由角色表推导**（`IntentPlan` 没有 tool 入口，
  因此计划证据与实际执行天然一致）；`intent`、`prefetch_tools` 不放权；
  通行问题、规则路由关闭、模型已降级时一律不规划；规划调用独立超时且
  **不计入熔断**，失败静默回落规则计划；
- 13 个工具由注册表统一校验 schema、权限、安全级别、超时和审计；
- 本地意图路由最多预取 2 个只读工具，外部 VLM 不自动预取；
- 模型工具调用累计最多 6 次，写工具只允许偏好意图，外部视觉工具只允许明确
  视觉意图；同轮成功只读结果进入缓存；
- 每次对话暴露
  `routing -> prefetch -> specialists -> llm -> tool_loop -> safety_review`
  阶段轨迹（规划来源并入 `routing` 阶段，阶段数量与顺序不变），并记录
  `cache_hit`、`policy_denied` 和拒绝原因；
- LLM 无通行授权权，最终回复仍经过确定性安全守门员复核；状态保留原始回复、
  最终回复、改写动作类型（原样 / 追加说明 / 整句替换）、危险措辞复核和幂等结果。

```powershell
python scripts\agent_runtime_audit.py `
  --base-url https://api.deepseek.com/v1 `
  --api-key $env:BLINDGUARD_AGENT_LLM_API_KEY `
  --model deepseek-chat `
  --output evaluation\agent_runtime_audit_online.json
```

### 1.2 安全行为

`tests/test_safety_policy.py` 和 `test_agent_tools.py` 验证：

- 红灯/黄灯/未知灯色/无检测/高风险问题绕过 LLM；
- 绿灯不输出通行许可；
- 危险 LLM 回复被替换；
- 即使用户不是询问过街，回复中的通行授权措辞也会被拦截；
- 红灯主动播报走本地模板；
- 普通环境问题仍可完成工具调用循环；
- 复合问题（"能否过街 + 我该往哪站"）先确定性拒绝通行，再用导航工具
  补非通行建议，且补充文案全部来自工具输出，不自撰可能被判为授权的内容。

安全策略与真实数据缺口说明见 `docs/安全策略.md`。

### 1.3 智能体可解释证据（现场可核对）

这些证据不需要读代码或看日志，直接在页面与接口上可查：

| 证据 | 位置 | 说明 |
|---|---|---|

   - 需对连续视频逐帧或关键帧标注，按场景、类别和漏检/误检分别统计；
   - 模型 SHA256、输入尺寸、裁剪开关与匹配阈值由工具自动写入报告，避免口径漂移；
   - 工具在存在未人工校正帧时**拒绝写入报告**，防止"拿模型预测评模型"的数字进答辩材料。

   两条口径不可互相引用：

   | 命令 | 测什么 | 引用时的表述 |
   |---|---|---|
   | `evaluate.py accuracy --data …` | 单模型 + ultralytics val，离线测试集 mAP | "模型离线验证集指标" |
   | `evaluate.py e2e --labels …` | 生产管线（主辅双模型 + 裁剪 + 合并 + 灯色）在人工真值上的精确率/召回率 | "当前部署配置端到端指标" |

   ```powershell
   # 逐帧核对 evaluation/e2e_labels.json：删误检、改类别、补漏检、填 light_state，
   # 确认过的帧把 auto_filled 改成 false
   python evaluate.py e2e --labels evaluation/e2e_labels.json
   ```

2. **真实视障用户测试**
   - 至少 5-8 位用户，全盲与低视力分组；
   - 需要知情同意、陪护和可随时终止机制；
   - 方案见 `docs/用户测试方案.md`。

3. **第一人称 POV 数据**
   - 需真实头戴、胸前或导盲辅助设备视角；
   - 需授权、脱敏和场景隔离；
   - 规范见 `docs/pov_data_collection.md`。

4. **通行安全的实地验证**
   - 必须由陪护人员在封闭或受控道路完成；
   - 需要统计“错误授权次数”，目标必须为零；
   - 需要分别记录漏检、误检、灯色错误和交互延迟。

在完成这些工作前，不能声称：

- “真实准确率达到 90% 以上”；
- “已经通过视障用户验证”；
- “可以替代盲杖或保证安全过马路”；
- “合成 100% 等同于实拍 100%”。

建议按以下顺序展示：

1. **问题真实**：视障出行、主动预警、中国道路定制类别；
2. **技术闭环**：双模型检测、跟踪、风险、场景、Agent、语音；
3. **工程可信**：统一生产管线、令牌认证、模型指纹、离线降级、CI；
4. **安全可信**：确定性护栏、红灯硬拒绝、绿灯不授权、危险 LLM 输出拦截；
5. **智能体可信**：10 角色 / 13 工具的台账、阶段轨迹、决策依据与安全改写对照，
   全部在页面上可核对，不需要读日志；

7. **诚实边界**：真实用户、POV 数据和当前配置端到端准确率仍需实测；

## 5. 常见评委问答

### “为什么不直接让大模型判断能不能过马路？”

因为 LLM 是概率组件，网络、延迟、幻觉和未知分布都可能改变结果。
BlindGuard 让 LLM 负责环境理解和表达，通行许可由确定性安全层控制；
红灯、黄灯、未知灯和高风险场景根本不进入 LLM 决策路径。

### “绿灯为什么还不能走？”

绿灯只说明局部裁剪中检测到绿色，不能证明方向正确、没有转弯车辆、
用户位置正确或没有遮挡。系统不把感知结果包装成安全认证。

### “没有检测到障碍，为什么不能说安全？”

漏检本身就是导盲系统的主要风险。摄像头没看到，不等于环境没有危险。
因此无检测结果统一回答“无法判断”，而不是“安全”。

### “和 Seeing AI / Be My Eyes 有什么不同？”

BlindGuard 是持续、主动的风险感知和语音预警系统，并针对井盖、盲道、
公共设施等中国道路类别训练辅助模型；不是每次由用户举手机拍照的被动工具。

### “目前最需要补什么？”

当前最需要的是第一人称授权数据、当前部署配置的连续视频标注，以及真实
视障用户内测。安全护栏解决“不错误授权”，真实数据才能回答“实际好不好用”。
